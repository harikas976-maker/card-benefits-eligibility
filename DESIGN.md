# Eligibility service design

**Identity and audit.** The test authentication hook accepts only two synthetic bearer identities. The route rejects a mismatched customer ID before calling either client and always queries the profile using the authenticated subject. The response contains a decision, reason, and generated correlation ID. A successful response requires an audit write. The production priority is a shared durable audit sink with encryption, restricted write and read roles, and an explicit retention policy.

**Failures and capacity.** Profile and rules reads run in parallel. Each attempt has a 100 ms connection budget and a 300 ms total budget. A network failure or HTTP 429, 502, 503, or 504 permits one retry after 25-50 ms of jitter. Other statuses and malformed responses fail immediately. A single retry caps amplification at two calls per dependency, while jitter spreads retry arrivals. Either dependency failing yields a temporary 503 with no eligibility decision. Each process admits up to 32 in-flight eligibility checks and rejects excess work immediately. Capacity reopens as checks finish.

**Memory incident.** For growth from 115 MB to 800 MB, graph RSS, heap used and total, external and array-buffer memory, GC activity, request count, and concurrency. Compare equivalent points after major collections during repeated synthetic load and idle cycles. A rising post-GC heap floor suggests retention. Stable heap with elevated RSS warrants checking native buffers, allocator behavior, and OS memory maps. In a drained, disposable replica with enough headroom, capture snapshots before and after reproducing growth. Snapshots pause the process, can temporarily double heap usage, and can contain sensitive data. Restrict and encrypt access, use synthetic traffic where possible, and expire the files. Compare retained sizes, inspect dominators, and trace retaining paths to a root such as a cache, listener, or unresolved promise. Cap the affected workload and recycle instances if needed while fixing the retaining reference. More replicas can buy capacity while the underlying growth continues.

**Scaling and deployment.** Compare CPU, event-loop delay, per-dependency latency and errors, and rejected work before scaling. Add instances for sustained CPU saturation or independent concurrency demand when downstreams have spare capacity. If downstreams are already saturated, bound demand and investigate there first. An initial alert could flag 503s above 1% for five minutes at meaningful traffic. For AWS, bundle the compiled API and production dependencies and use a Fastify Lambda adapter behind API Gateway HTTP API. Replace local test auth with verified authorizer identity and the local audit writer with the shared sink. Initialize clients outside the handler and reuse connections across warm invocations. Keep the bundle small, use provisioned concurrency if latency targets justify it, and set reserved concurrency against downstream budgets. Inject configuration through environment settings and fetch secrets from managed storage. For Azure Functions, use an HTTP trigger on a supported Node runtime, configure identity and concurrency for the hosting plan, and track dependency latency and failures in Application Insights.
